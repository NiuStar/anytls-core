# Chrome 155 后端与 Go 1.27.3 接入（候选）

本次按“尽量与 Chrome 特征一致、减少 Go／AnyTLS 固定模式”的目标接入新 TLS 后端，不以 Go TLS1.3-only 取代该目标，也不承诺完整浏览器等价或不可识别。

## 固定版本

- Go 官方下载清单核实最新稳定版为 **go1.27.3**。候选源码、CI、源码安装器、构建校验和对应源码打包统一固定该版本，不在用户安装时追随浮动 latest。
- 新后端固定 `github.com/refraction-networking/utls v0.0.0-20261006195536-6ebdceb2607e`，对应 Chrome155 完整实现引入提交。选择该提交而非当前头，避免无关的依赖全集升级；实际构建选择仍需核实。
- 现有 MetaCubeX uTLS 依赖保留，不全局替换，避免 Reality、会话 ID 和内部优化消费者的接口／类型冲突。

## 范围

在独占引擎服务上下文注册新 Chrome 工厂；认证 SDK 私有补丁只让普通 AnyTLS、启用 uTLS、指纹为空或精确 chrome、没有 Reality／其他 engine 覆盖时调用它。缺工厂明确拒绝，不能自动退回旧 Chrome。显式其他指纹与旧消费者仍走原路径。

新适配器使用完整上游 Chrome155 实现，包括 Trust Anchors 和 ML-DSA 验证能力，不通过 generic 扩展编号伪造支持。原有 CA／SPKI／SNI、明确跳验授权、上下文超时与关闭保持；尚未支持的关键高级 TLS 选项明确拒绝，不静默忽略。

升级允许修改 `go.mod`、`go.sum`、源码、CI 和安装器，不要求与旧版本逐字节不变。修改完成后重新冻结候选，并绑定新的 SHA；冻结后的测试过程不得静默修改输入，否则须重新冻结并复测。构建 wrapper 的 `root_inputs_unchanged` 仅比较同一次命令开始与结束时的输入，不比较升级前后版本。

原 Start 清理及 core-slim 补丁输入／结果身份保持，新增 Chrome hook 单独绑定源码／补丁／结果 SHA，并纳入构建回执和源码交付。原模块缓存不修改；需要变更的第三方源码在认证私有副本中修改。

## 已有证据与本次门禁

独立探针已在 Go1.27 下，对本机 Chrome156.0.8078.47 与 Chrome155 各三份首 ClientHello 比较：GREASE 归一化后八项观察字段一致，补齐旧 Chrome133 的扩展51764及三个签名算法差异。此结论只是探针，不是本次内嵌成品。

接入必须再通过：真实应用编译→AnyTLS→严格 CA／公钥固定认证→TCP／UDP，错误身份／密码零目标载荷；新编译 CLI 与同端点 Chrome 的实际握手差分；完整回归、vet/build、缺 uTLS 拒绝、克隆和生命周期；源码安装及 CCS 许可／身份规则。Go1.27 更换对旧 fork 的兼容性也必须由实际构建证明。

- 完整二进制已链接固定 refraction uTLS 和旧 MetaCubeX uTLS。二进制 SHA-256：`3d4cf921f1fdfcc00ed214fc0cfc1610f975b093fa3ce8057ae16c6bf3b4fb38`。
- 完整 CLI 与实际 Chrome 各三份首 Hello 比较：默认／Chrome 的八项归一化字段全部匹配；显式 Go 对照有差异。仅八字段一致，不声称长度、扩展顺序分布、恢复或记录时序等价。
- 正式公开 anytls-go v0.0.28 二进制：三种模式×正确认证／错误 SPKI／错误密码，共九例通过；错误认证目标零连接／零载荷，所有测试进程和端口回收。
- 普通用户独立 WebUI 启动、登录／会话读回、Origin／CSRF 拒绝、静态资源 SHA 校验通过，测试后关闭。未安装特权助手、未修改或重启生产程序／VPN。

原始 v1 模块准备、v2 测试格式、v3 SDK API、v4 缺 uTLS 诊断及 WebUI 测试布局错误保留，不追改为成功；修正后分别新候选重跑。升级阶段允许修改输入，只在单次已冻结验收期间校验输入未漂移。

本次仅接入及隔离部署测试，不自动发布、安装助手、替换生产 WebUI 或重连生产 VPN。既有 TLS1.3-only／Chrome 组合的保守拒绝政策暂时保留，除非新后端另行通过真实版本门后再有范围明确的修订。
